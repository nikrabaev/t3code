# v0.1 build spec

Concrete, implementable specification for Weave v0.1 — terminal-grade, sequential, proves the DAG + Contract model end-to-end inside t3code. Read [concepts.md](concepts.md), [architecture.md](architecture.md), and [t3code-integration.md](t3code-integration.md) first.

## What v0.1 is

- A new `"weave"` value of `ProviderInteractionMode`.
- A Weave Run aggregate: create, compile Blueprint, approve, execute Nodes sequentially, exit.
- A minimal web UI: `/weave` slash command + Weave Run page showing sidebar chat + grouped-by-Phase Blueprint (list form) + Node inspector with child-thread `ChatView`.
- No parallelism. No PendingDecisions UI. No Phase gate smoke tests. No Redesign mode. No graph canvas.

## What v0.1 is **not**

Deliberately out of scope. Defer until v0.2+:

- Parallel dispatch, scope enforcement hooks, React Flow graph, merge-driver.
- PendingDecision surfacing, pre-auth DSL, auto-decision log.
- Phase smoke tests, "Chat before deciding," Vision editing mid-run.
- Redesign mode, Blueprint version diffing.
- Contract Amendment flow, failure subdivide/escalate ladder.
- Intervene-in-running-Node (pause/resume/restart).

## The four slices

| Slice | Work                                             | Output                                                                                          |
| ----- | ------------------------------------------------ | ----------------------------------------------------------------------------------------------- |
| 1     | Contracts extension                              | `weave.ts` + `orchestration.ts:93` change + `orchestration.domainEvent` union extension + tests |
| 2     | Decider + Projector + Invariants (pure)          | Three new pure TS files + unit tests                                                            |
| 3     | Engine + Scheduler + Planner + basic Reactors    | `WeaveEngine`, `WeaveScheduler` (sequential), `WeavePlanner`, `WeaveContractConformer` (naive)  |
| 4     | Web — routes, components, `/weave` slash command | New routes + weave component tree + sidebar integration + store                                 |

Each slice typechecks and tests on its own before the next. Build in order.

### 1.6 Commands

Follow t3code's existing command conventions: `type` discriminator, branded `CommandId`, `createdAt: IsoDateTime`. Split commands into **dispatchable** (user-initiated via RPC) and **internal** (server reactors only), mirroring the existing `DispatchableClientOrchestrationCommand` / `InternalOrchestrationCommand` split.

**Dispatchable (user-initiated):** `weave.create`, `weave.blueprint.approve`, `weave.phase.approve`, `weave.decision.resolve`, `weave.exit`.

**Internal (server-only):** `weave.blueprint.compile`, `weave.node.dispatch`, `weave.node.verified`, `weave.node.failed`.

Each command is a `Schema.Struct` (no helper) with `type` as discriminator. `createdAt` sits at the end of each struct. The client generates `WeaveRunId` up-front for idempotency and includes it in `WeaveCreateCommand`.

### 1.8 Extend `OrchestrationEvent` union and `OrchestrationAggregateKind`

The envelope wrapping happens in `orchestration.ts`, not in `weave.ts`. Three changes there:

1. **Extend `OrchestrationAggregateKind`** to include `"weave"` alongside `"thread"` / `"project"` etc.
2. **Extend `aggregateId`** in the event envelope so it can carry `WeaveRunId` in addition to the existing ID types. v0.1 uses a plain union at the envelope boundary; Slice 3 will introduce a proper discriminated `(aggregateKind, aggregateId)` correlation (see the Slice-3 debt item below).
3. **Extend the `OrchestrationEvent` union** to include the Weave payload structs, each wrapped with the standard envelope fields (`eventId`, `sequence`, `aggregateKind`, `aggregateId`, …).

Inspect the concrete shape of `OrchestrationEvent` and the `EventBaseFields` helper in `orchestration.ts` before extending — don't recreate the envelope, reuse it.

The same pattern applies to `DispatchableClientOrchestrationCommand` / `InternalOrchestrationCommand` / `OrchestrationCommand`: union-extend them with the Weave command variants so the existing RPC path routes them correctly.

**Known debt flagged during Slice 1** (to resolve in Slice 3): the `aggregateId` field is typed as `ProjectId | ThreadId | WeaveRunId` (a plain union). A proper discriminated correlation would pair each `aggregateKind` value with its valid ID type, eliminating four `as ProjectId | ThreadId` casts introduced in the downstream `apps/server` stubs. Not a v0.1 blocker; ships in Slice 3 with real decider/projector logic.

### 1.9 Tests

File: `packages/contracts/src/weave.test.ts`

Cover:

- Encode / decode round-trip for each struct (use `Schema.decodeSync` with minimal fixtures).
- `WeaveRun` with default `status = "draft"`, `concurrencyCap = 1`.
- `Blueprint` with at least one Node and Phase validates.
- `Blueprint` with a Node whose `phaseId` doesn't match any `WeavePhase.id` — **deferred to Slice 2's invariants.** Schema-level can't cheaply check array membership across sibling arrays in Effect Schema; enforce it in `weaveCommandInvariants.ts` instead.

- Each event payload decodes successfully with valid fixture.
- `OrchestrationCommand` union decodes each Weave command variant alongside existing thread variants.
- `OrchestrationEvent` union decodes each Weave event (envelope + payload) alongside existing thread event variants.

Use `@effect/vitest`. Follow the pattern in `orchestration.test.ts`.

### 2.3 Decider cases (v0.1 subset)

For each command, the decider either returns events or an `InvariantError`.

| Command                   | Valid when                                                             | Emits                                                                                                                                                                                                                                  |
| ------------------------- | ---------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `weave.create`            | run does not exist                                                     | `weave.created`                                                                                                                                                                                                                        |
| `weave.blueprint.compile` | run in `draft` (initial) or `running`/`reviewing` (amendment/redesign) | — _(compile is a side effect triggered by reactor; no event emitted by decider. The planner emits `weave.blueprint.compiled` directly.)_                                                                                               |
| `weave.blueprint.approve` | run has `currentBlueprintVersion` matching command; run in `reviewing` | `weave.blueprint.approved` + run status transition to `running`                                                                                                                                                                        |
| `weave.node.dispatch`     | run in `running`; node in `ready`; ancestors all `verified`            | `weave.node.dispatched` + node status transition to `running`                                                                                                                                                                          |
| `weave.node.verified`     | run in `running`; node in `running`; outcome non-empty                 | `weave.node.verified`. If node was last in its Phase → implicit `weave.phase.gated` (v0.1 omits explicit gate UI, so this becomes pseudo-auto-approve in v0.1). If node was last in final Phase → run status transition to `complete`. |
| `weave.node.failed`       | run in `running`; node in `running`                                    | `weave.node.failed`                                                                                                                                                                                                                    |
| `weave.decision.resolve`  | decision open                                                          | `weave.decision.resolved`                                                                                                                                                                                                              |
| `weave.phase.approve`     | phase pending                                                          | `weave.phase.approved` + (if last phase + approved) run status → `complete`                                                                                                                                                            |
| `weave.exit`              | run not already `complete` or `aborted`                                | `weave.exited`                                                                                                                                                                                                                         |

### 2.4 Projector cases

Each event applies an idempotent state update to `WeaveRunProjection`:

| Event                      | Update                                                                                                               |
| -------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| `weave.created`            | materialize new `WeaveRun`, status = `draft`, concurrencyCap = 1 (default)                                           |
| `weave.blueprint-compiled` | set `currentBlueprint`, transition status to `reviewing`, hydrate `nodeStatuses` (all `pending`) and `openDecisions` |
| `weave.blueprint-approved` | set `currentBlueprintVersion`, status = `running`, `concurrencyCap` applied                                          |
| `weave.node-dispatched`    | set `nodeStatuses.get(nodeId) = "running"`, set `childThreads.get(nodeId)`                                           |
| `weave.node-verified`      | set `nodeStatuses.get(nodeId) = "verified"`                                                                          |
| `weave.node-failed`        | set `nodeStatuses.get(nodeId) = "failed"`                                                                            |
| `weave.decision-resolved`  | remove from `openDecisions`, append to `autoDecisionLog` if `byUser === false`                                       |
| `weave.phase-approved`     | update `phaseApprovals`                                                                                              |
| `weave.exited`             | status = `complete` or `aborted`                                                                                     |

### 2.5 Invariants (sample)

- A `weave.node.dispatch` command must name a node that exists in `currentBlueprint.nodes`.
- `weave.blueprint.approve` must reference the current (not stale) version.
- `weave.decision.resolve` cannot target a resolved decision.
- No command accepted when run status is `complete` or `aborted` (except reads).

### 2.6 Tests

Per-command unit tests covering happy path + at least one invariant violation per command. Follow `decider.*.test.ts` patterns already in the repo.

- [ ] All pure; no IO. No `Effect.sync` wrappers. Plain functions.
- [ ] `bun run test` green.

### 3.1 Files

| File                        | Purpose                                                                                                                                                                       |
| --------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `WeaveEngine.ts`            | Public service; persists events, emits domain events, single writer to each Run                                                                                               |
| `WeaveScheduler.ts`         | `DrainableWorker`; reacts to events, decides next action (dispatch / wait / complete)                                                                                         |

### 3.2 Scheduler behavior (v0.1 = strictly sequential)

State machine:

1. On `weave.blueprint-approved` → compute initial ready set from the Blueprint's DAG.
2. Pick the first ready Node (in `dependsOn`-topological order, then by Phase ordinal, then by Node `id`).
3. Allocate a worktree (reuse existing `GitCore` plumbing — new branch off the project's base branch).
4. Issue `weave.node.dispatch`.
5. Dispatch handler: create child thread (`thread.create` with `weaveChild: { runId, nodeId }` metadata, `interactionMode: "default"`, `worktreePath` set), issue `thread.turn.start` with the Node payload.
6. Wait for `turn.processing.quiesced` receipt on `RuntimeReceiptBus`.
7. On quiesce → `WeaveContractConformer` runs → emits `weave.node.verified` or `.failed`.
8. On verified → update projection → goto 2.
9. On no-more-ready-nodes AND no-running-nodes → emit run completion events.

v0.1 does not handle:

- Parallel dispatch (concurrency cap is enforced at 1).
- PendingDecision gating (v0.1 planner must produce a Blueprint with zero PendingDecisions).
- Phase gate smoke tests (run status transitions straight to `complete` after last Node).

### 3.3 Planner behavior

`WeavePlanner` is a thin wrapper around `ProviderService`:

- System prompt: "you are the Weave planner. Given the Vision below and the (optional) snapshot, produce a Blueprint conforming to the schema in `@t3tools/contracts/weave`. Extract scaffold/contract/utility Nodes up front; ensure every sibling group's shared concerns are hoisted to ancestors via Contracts; do not emit PendingDecisions for v0.1."
- User message: the Vision + snapshot.
- Expected output: a JSON Blueprint. Parse + validate via `Schema.decode(Blueprint)`. On failure, retry once with error context. On second failure, emit a pseudo-event that transitions the run back to `draft` with an error message — let the user fix their Vision and retry.

### 3.4 WeaveContractConformer — v0.1 naive

For v0.1:

- Verifier is uniformly: "run `bun run test` in the Node's worktree. Exit code 0 → verified. Nonzero → failed."
- Ancestor-authored conformance tests are not yet materialized (v0.2 adds `conformance.test.ts` writing). Tests in v0.1 are whatever the Node itself produced during its turn.

### 3.5 Definition of done

- [ ] Creating a Weave Run end-to-end via RPC results in a Blueprint and sequential execution completing.
- [ ] Existing t3code tests still green.
- [ ] New integration test: a Weave Run with a 3-Node Blueprint (scaffold → contract → raw) completes sequentially against a stub provider.
